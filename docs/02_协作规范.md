# 团队协作规范（Godot 4.5 Mono C# / 48h GameJam）

> 目标只有一个：**让 2–3 个程序同时写代码、同时编辑 Godot 工程，而不把彼此的活儿弄坏。**
> 本文件的配置部分（§2）**原样复制到仓库**即可，不需要改动。

---

## 1. 协作策略：全员单分支 + 高频提交（v2 定案）

> **不使用分支。** 所有人直接在 `main` 上工作。
> 理由：团队对 Git 和引擎都是 0 基础，且代码完全依赖各自的 AI 生成 —— 分支的心智成本
> 远大于收益。冲突靠**缩短冲突窗口**（高频提交）和**缩小冲突面**（文件所有权）来控制，
> 而不是靠分支隔离。

### 1.1 四条硬规则 ⭐

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **提交前先 `git pull --rebase`**，再 `git push` | 都在 main 上，不 pull 就会 push 失败 |
| 2 | **明令禁止 `git push -f` / `--force`** | ⚠️ push 被拒时新手最容易搜到 force push，一下就把别人的代码冲掉了。**这是单分支下最危险的操作，没有之一** |
| 3 | **⭐ 给你们各自的 AI 加"文件边界"约束** | 见 §1.2，这是单分支下的头号冲突源 |
| 4 | **pitch 时说文件名，不说功能名** | 见 §1.3 |

### 1.2 ⭐ 给 AI 的文件边界约束（最重要的一条）

**问题**：AI 默认会"顺手优化"整个项目。程序 A 让 AI 改玩家移动，AI 可能顺手把 UI 布局、
事件总线、别人的脚本一起重构了。单分支下，这些改动会直接进 main，把别人的活儿冲掉。

**解决**：每个人在给 AI 的提示词里，**必须**带上这段约束（复制粘贴即可）：

```
你是本项目【程序 X】，负责模块：src/Combat/ src/Player/ src/Bullets/

严格要求：
1. 只允许创建和修改上面这些目录下的文件。
2. 绝对不要修改、删除、重构其他任何目录的文件，即使你认为它们有 bug 或写得不好。
3. 如果你认为其他模块需要改动，不要动手，只在回复里告诉我"需要程序 Y 改 src/XXX/YYY.cs 的
   某个地方，原因是……"，由我去沟通。
4. 不要修改 project.godot、任何 .tscn 场景文件、其他人的 .cs 文件。
5. 如果确实需要新增一个跨模块事件，在 src/<你的模块>/Events.cs 里定义 struct，
   通过 Bus.Pub / Bus.Sub 通信，不要直接引用其他模块的类。
```

> **这条约束的效果，比任何 Git 技巧都大。** 建议直接存成项目根目录下的 `AI_RULES.md`，
> 每人复制自己那一段。

### 1.3 Pitch 规范（每次提交前，30 秒）

在群里发一条：

```
我要提交了，改的是：
- src/Player/PlayerController.cs （新增加速度与无敌帧）
- src/Combat/DamageSystem.cs （加 Canceled 标志）
没人也在动这两个文件吧？
```

**规则：**
- **说文件名**，不说"我做了敌人 AI" —— 别人一听就知道要不要避让
- 如果有人回"我在改"，等他提交完你再 pull
- 没人回就 30 秒后直接提交

### 1.4 提交频率

| 场景 | 频率 |
|---|---|
| 正常开发中 | **每 15–30 分钟一次**。冲突窗口 = 两次提交之间的时间，窗口越短冲突越小 |
| 改完一个能跑的小功能 | 立刻提交 |
| 一天中的强制同步点 | 开工时、午饭后、收工前，全员 pull 并跑一次游戏 |

### 1.5 常用命令（只会这四个就够了）

```bash
git pull --rebase          # 开工前 / 提交前：拉取别人的改动
git add -A                 # 暂存
git commit -m "feat(player): 加了无敌帧"   # 提交
git push                   # 推送
```

**如果 push 被拒绝**：说明别人先提交了。执行 `git pull --rebase` → 有冲突就解决 → 再 `git push`。
**永远不要用 `git push -f`。**

### 2.2 `.gitattributes` ⭐ 本文件最重要的四行

```gitattributes
# 统一换行符，杜绝 Windows CRLF 造成的"整个文件都在冲突"
* text=auto eol=lf

# ⭐⭐ 把 Godot 场景与资源标记为二进制 ⭐⭐
# 原因：.tscn 是文本，Git 会"尝试"自动合并并经常"看起来成功"。
# 但合并后的场景结构往往已被破坏 —— Godot 打开后节点丢失、脚本引用失效、甚至打不开。
# 标记为 binary 后，Git 遇到冲突会直接报"二进制冲突"，逼人去处理，
# 而不是悄悄给你一个坏文件。这是 Godot 多人协作最关键的一条配置。
*.tscn binary
*.tres binary
*.scn  binary
*.res  binary
*.godot binary
```

### 2.3 `.editorconfig`（仓库根目录）

```editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true

[*.cs]
indent_size = 4

```

## 3. 极高危文件清单（变更申请制）

以下文件**一旦冲突，损失巨大**。规定：**只有指定负责人能改，其他人需要改就在群里 @ 他，说清楚要加什么。**

| 文件 | 风险 | 负责人 | 别人需要改时 |
|---|---|---|---|
| **`project.godot`** | ⚠️⚠️⚠️ Autoload 列表、InputMap、图层名、物理设置全在这里。损坏 = 工程打不开 | 程序 A | 群里说 "帮我加个 Autoload：XXX"，A 统一加 |
| **Autoload 列表** | 顺序敏感，且新人容易加重复 | 程序 A | 同上 |
| **`InputMap`（输入映射）** | 全项目共用，改一下可能影响所有人 | 程序 A | 同上 |
| **`Main.tscn` 主场景** | 如果它变成"大杂烩"，就成了冲突中心 | 程序 A | **建议：主场景保持极简，逻辑用 C# 运行时组装**（见架构文档 §0 铁律③） |
| **`*.csproj`** | Godot 增删文件会自动改写它 | 任意 | 冲突时**直接删除让 Godot 重新生成**，不要手解 |
| **`scenes/` 下任何一个 `.tscn`** | 二进制标记后无法自动合并 | 见 CODEOWNERS | 必须找归属人，或让他先提交 |

### 主场景的正确做法

```
Main.tscn 里只放：
  ├── Main (Node, 挂 Main.cs)      ← 唯一有脚本的节点
  └── （空）

Main.cs 的 _Ready() 里：
  AddChild(Player.Instantiate());
  AddChild(UIManager.Instantiate());
  AddChild(RunDirector.Instantiate());
  ...
```

这样 `Main.tscn` 从头到尾几乎不变，**冲突源头直接消失**。

## 4. 命名规范

统一命名 = 减少"找不到东西"的时间，也减少 Git 里大小写引发的幽灵冲突。

| 类型 | 规范 | 示例 |
|---|---|---|
| C# 类 / 文件名 | `PascalCase`，**文件名必须等于类名** | `PlayerController.cs` |
| 命名空间 | `项目名.模块名` | `namespace MyGame.Combat;` |
| 私有字段 | `_camelCase` | `private float _moveSpeed;` |
| 公共属性 / 方法 | `PascalCase` | `public float GetDamage()` |
| 常量 | `UPPER_SNAKE` | `const uint LAYER_PLAYER = 1 << 0;` |
| 事件结构体 | 过去式名词，`PascalCase` | `EntityDied`、`RoundWon`、`RoundLost` |
| 场景文件 | `snake_case.tscn` | `enemy_slime.tscn`、`upgrade_picker.tscn` |
| 资源文件 | `snake_case.tres` | `slime.tres`、`upgrade_crit_up.tres` |
| 美术资源 | `模块_对象_动作_序号` | `enemy_slime_idle_01.png` |
| 节点名 | `PascalCase`（Godot 默认） | `HitBox`、`Sprite2D` |
| 场景唯一名 | `%` 前缀引用 | `GetNode<Sprite2D>("%Sprite")` |

**枚举集中定义**：所有 `PlayerStat` / `EnemyStat` / `Rarity` / `ModifierOp` 这类跨模块枚举，统一放 `src/Core/` 并在 Day1 冻结。

## 5. 提交规范

格式：`<类型>(<模块>): <一句话>`

```
feat(player): 加入无敌帧与闪烁提示
fix(combat): 修复无敌期内仍扣敌人血的问题
data(upgrades): 新增 6 个玩家词条，下调闪现权重
perf(pool): 子弹对象池化，同屏 200 弹不卡
feat(run): 失败重打本轮，轮次不推进
refactor(ui): HUD 改为纯事件驱动
```

类型：`feat` / `fix` / `data` / `perf` / `refactor` / `art` / `audio` / `chore`

**两条硬规则：**

1. **提交前必须能编译、能跑**。如果"我知道它还跑不起来但我先提交"，请在 commit 信息末尾加 `[WIP]`，并在群里说明。
2. **不要提交 `.godot/` 里的东西**。如果 `git status` 里出现 `.godot/`，说明 gitignore 没生效，先停下来修。

## 6. 场景编辑冲突预防

Godot 场景是单人编辑制的，没有自动合并。除了 CODEOWNERS，再加三条：

### 6.1 场景最小化原则

每个 `.tscn` 只描述**一个实体**：

```
✅ player.tscn（只有角色节点树）
✅ enemy_slime.tscn
✅ hud.tscn
❌ game_world.tscn（里面有玩家、敌人、UI、管理器…… = 定时炸弹）
```

### 6.2 需要改别人的场景时

> 流程：**先 pull → 群里喊一声"我要改 enemy_slime.tscn，5 分钟" → 改完立刻 commit + push → 群里说"好了"**。

### 6.3 协同的替代方案（推荐）

能不编辑场景就不编辑场景：

- 数值改动 → 走 `.tres`，不要打开场景改 Inspector
- 节点结构 → 用 C# 在运行时 `AddChild`
- UI 布局 → 用容器（`HBoxContainer` / `VBoxContainer` / `MarginContainer`）而非绝对坐标，这样加节点不破坏现有布局

## 7. 冲突应急预案

### 情况 A：`.cs` 文件冲突

正常解决。如果看不懂对方改了什么，**直接找他一起看，30 秒解决的事别自己猜 10 分钟。**

### 情况 B：`.tscn` / `.tres` 报告"二进制冲突"

**不要试图手动编辑 `.tscn` 文本文件。** 正确流程：

```bash
# 二选一：保留我的
git checkout --ours  path/to/scene.tscn
# 或：保留他的
git checkout --theirs path/to/scene.tscn

git add path/to/scene.tscn
```

然后**打开 Godot，把丢掉的那部分改动重新做一遍**。通常 2 分钟的事。
如果两边改动都很大且都很重要 —— 让改动少的那个人重做，改动多的那个保留。**永远不要让两个人同时精修同一个场景。**

### 情况 C：`project.godot` 冲突

```bash
git checkout --theirs project.godot   # 以负责人（程序 A）的版本为准
```
然后重新让 A 加你需要的东西。

### 情况 D：`.csproj` 冲突

```bash
rm 项目名.csproj
# 回到 Godot，它会自动重新生成
```

### 情况 E：工程打不开 / 脚本全红

按顺序试：
1. 回到 VS Code，`Ctrl+Shift+B` 重新构建，看是否有编译错误（**90% 的"脚本变红"其实是编译失败**）
2. 删除 `.godot/mono/` 缓存目录，重开工程
3. `git status` 看是不是误提交了什么

## 8. 48 小时协作节奏

| 时点 | 动作 | 耗时 |
|---|---|---|
| **D1 00:00** | 建工程 + 全员拉仓库 + 写好各自的 `AI_RULES.md` 约束段 + 配置校验（各人 `git status` 应干净） | 30 min |
| **D1 01:30** | **契约评审**：`Core/` 七件套 + `PlayerStat`/`EnemyStat` + 事件清单，三人一起过一遍。**过了就冻结** | 30 min |
| 每 15–30 分钟 | pitch → `git pull --rebase` → `git add -A` → commit → push | 1 min |
| 每 4 小时 | 全员 pull → 跑一次游戏确认没坏 | 5 min |
| **D1 12:00** | **第一次完整整合**，出一个能玩的包 | — |
| **D2 每天开始** | 站会 10 分钟：昨天做了什么 / 今天做什么 / 有什么阻塞 | 10 min |
| **D2 36:00** | **功能冻结（Code Freeze）**，此后只修 bug 和调数值 | — |
| **D2 44:00** | 出包、写说明、提交作品页 | — |
