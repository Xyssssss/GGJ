# 团队分工与上手指南

> 适用：策划兼程序 1 人（你）+ 程序 2 人（均 0 基础）+ 美术/音频 1 人（可能兼程序）
> 周期：48h GameJam　|　引擎：Godot 4.5.1 Mono C#
> 配套文档：`01_项目架构方案.md`（技术契约）· `03_策划案_GDD.md`（设计）· `AI_RULES.md`（AI 提示词约束）

---

## 1. 先认清现状：他们缺的不是编程能力

队友是**程序专业**，意味着 C# 语法、数据结构、算法、状态机他们都会。
真正卡住他们的是**引擎操作**——"这个脚本挂在哪""Inspector 里那个框是啥""为什么按 F5 没反应"。

所以分工的核心原则是：

> **按「需要打开 Godot 编辑器的程度」分层，不按功能模块平铺。**

| 层 | 引擎接触度 | 典型工作 | 谁能做 |
|---|---|---|---|
| **L1 纯逻辑** | ⭐ 几乎为 0 | 枚举与数据类、`StatBlock`、词条抽取器、反射数学、RNG、轮次状态机 | **完全不会引擎的人当天就能出活**，只用 VS Code 写 `.cs` |
| **L2 半引擎** | 中 | 玩家控制器、炮弹、敌人、伤害管线、碰撞 | 需学会「挂脚本 / Inspector 改参数 / F5 运行」三件事 |
| **L3 场景层** | 高 | 场景搭建、UI 布局、动画、特效、Autoload 配置 | 需要较熟练的编辑器操作 |

**好消息**：L1 能覆盖的工作量比想象中大——词条系统、属性聚合、轮次流程这些"Roguelike 的肉"，
大部分是纯逻辑。**不会引擎的队友完全可以承担，而且能当天出活。**

## 2. 场景守门人制度（务必执行）

> **所有 `.tscn` 场景文件与 `.tres` 资源的创建、结构性修改，由固定 1 人负责。其他人一律不碰。**

| | 说明 |
|---|---|
| **为什么** | `.tscn` 是 Godot 团队协作的**头号冲突源**。两个程序同时改一个场景，Git 会"看似合并成功"，但文件结构其实已经损坏——表现为节点丢失、脚本引用失效、工程打不开。且**无法手动修复**，只能回滚 |
| **怎么做** | 把它变成**单人独占的文件类型**，冲突从根上消失 |
| **流程** | 其他人需要新场景 / 新节点 / 新资源时，在群里 @ 守门人并描述需求，由守门人创建 |
| **人选** | **学 Godot 最快的那个人**，不一定是技术最强的。此人开工前先花 2 小时看官方入门 |
| **配合** | `.gitattributes` 里把 `*.tscn` / `*.tres` 标记为 `binary`（见 `02_协作规范.md`），双保险 |

> 💡 对 0 基础团队，这条规则的价值**超过任何 Git 技巧**。
> 它同时解决了两个问题：① 最大冲突源消失；② 大部分人完全不用学编辑器。

## 3. 任务卡

每张卡 = 一个人可以在不被阻塞的情况下独立完成的工作单元。
**依赖**列标明了需要谁先交付什么。

### L1 纯逻辑卡（不用打开 Godot 编辑器）

| 卡 | 任务 | 产出文件 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **L1-1** | 枚举与数据类 | `src/Core/PlayerStat.cs`<br>`src/Core/EnemyStat.cs`<br>`src/Core/Layers.cs`<br>`src/Upgrades/*Data.cs` | 无 | 编译通过；策划能在 Inspector 里看到字段 |
| **L1-2** | 属性聚合器 | `src/Upgrades/StatBlock.cs` | L1-1 | 加 N 个修饰器后 `Get()` 返回正确聚合值；结算顺序 Add → Mul → Override |
| **L1-3** | ⭐ 词条抽取器 | `src/Upgrades/UpgradePicker.cs` | L1-1 | 纯随机加权抽 3 个不重复项；满层与互斥的被过滤；**保底至少 1 个机制类** |

## 5. Godot 最小知识包（给不会引擎的队友，15 分钟讲完）

> 打印或复制到群里。看完这份就能开始写 L1/L2 的代码。

### 5.1 五个概念

| 概念 | 一句话 |
|---|---|
| **Node（节点）** | 场景树里的一个对象。有名字、有父子关系、能挂脚本 |
| **Scene（场景）** | 一棵节点树，存成 `.tscn` 文件。相当于 Unity 的 Prefab |
| **Script（脚本）** | 挂在节点上的 `.cs` 文件，让节点有行为 |
| **Inspector（检查器）** | 选中节点后右侧的面板。脚本里标了 `[Export]` 的字段会在这里显示，**可以直接改数值不用改代码** |
| **Signal（信号）** | 事件机制。⚠️ **本项目不用它**，统一用 `Bus.cs`（见架构文档 §5.1） |

### 5.2 三个生命周期函数

```csharp
public override void _Ready()               // 节点进入场景树时调用一次 —— 初始化
public override void _Process(double delta)   // 每渲染帧调用 —— UI、动画、输入缓存
public override void _PhysicsProcess(double delta) // 每物理帧调用（默认 60Hz）—— 移动、碰撞
```

> **唯一需要背的规则**：**移动和碰撞相关的一律放 `_PhysicsProcess`**，其余放 `_Process`。
> 放错了会表现为"移动速度随帧率变化"或"碰撞穿透"。

### 5.3 四个必会操作

| 操作 | 怎么做 |
|---|---|
| 挂脚本 | 选中节点 → Inspector 最下方 → Script → `[空]` → 新建/选择 `.cs` |
| 改参数 | 选中节点 → Inspector 里找到标了 `[Export]` 的字段 → 直接改数字 |
| 运行 | **F5**（运行当前场景） / **F6**（运行主场景）。本项目用 F5 |
| 看报错 | 编辑器底部 **Output** 面板。C# 报错在 **MSBuild** 标签页 |

### 5.4 三条红线（违反会出大问题）

| # | 红线 | 正确做法 |
|---|---|---|
| 1 | ❌ 不要自己创建或修改 `.tscn` 文件 | 需要新场景/新节点 → **@ 守门人** |
| 2 | ❌ 不要用 `GetNode("路径")` | 用场景唯一名：`GetNode<Sprite2D>("%Sprite")`。改结构时不会断 |
| 3 | ❌ 不要用 `node == null` 判空 | 用 `GodotObject.IsInstanceValid(node)`。**Godot C# 里销毁后的节点不等于 null** |

### 5.5 构建方式（重要）

编辑器 → .NET → **关闭「自动重载项目」**（4.5 的 C# 热重载不稳定，多人协作时常出现脚本变红）。

统一流程：**VS Code 里 `Ctrl+Shift+B` 构建 → 回到 Godot 自动重载 → F5 运行**。
