## 0. 玩法定案（架构的一切前提）

| 项 | 定案 |
|---|---|
| 视角与移动 | **2D 横版，无重力单屏竞技场**。玩家上下左右自由移动，无跳跃 |
| 相机 | **固定不动**（单屏），只需震屏，不需要跟随逻辑 |
| 玩家 | 3 血，屏幕中心出生 |
| 射击 | 鼠标左键，初始**固定向正右方**，不可瞄准；CD 由策划配置 |
| 炮弹 | 伤害 1，命中即销毁（无穿透），出屏销毁 |
| 敌人 | 1 血，从屏幕**右边缘**出生，**默认向正左方水平移动** |
| 敌人移动 | ⭐ **光学反射**：**入射角 = 反射角**，**四条边全部反弹**，速度大小不变，**不追踪玩家**。默认 `vy = 0`（垂直入射 → 原路返回，是特例）。实现见 §5.6 |
| 碰撞 | 玩家碰敌人：双方各 -1 血；玩家进入无敌帧（默认 1.5s） |
| 无敌帧 | 期间再次碰撞，**双方都不结算**（防贴脸站撸） |
| 轮次 | ⭐ **波次制**：每轮分若干波，波间固定 CD，每波同时出若干敌人 |
| 胜利条件 | **双条件**：所有波次已刷完 **且** 场上敌人清空 |
| 胜利 | 三选一**强化敌人** → 进入第 N+1 轮 |
| 失败 | 三选一**强化自己** → **重打第 N 轮**（轮次不推进） |
| 轮次推进 | **只有胜利才推进**。轮次 = 难度层数 |
| 强化 | **永久累加**，玩家线与敌人线各自独立成长 |
| 血量 | **每轮开始回满 3 血** |
| 选卡 | 三选一时**完全暂停**游戏 |
| 终局 | 打满 **N 轮**后结算，评级按**总失败次数**（越少越好） |
| 边界 | 玩家撞屏幕边缘停住（不反弹） |

### 这个设计的两个关键推论（架构必须支撑）

1. **失败 = 保底机制**。卡在某一层时，每失败一次玩家就变强一点，最终一定能过。这决定了 `RoundDirector` 必须能"重打本轮"，且**重打时敌人配置完全不变、玩家带着新 buff**。
2. **评级按总失败次数**。这抑制了"故意送死刷 buff"，激励自洽。所以统计模块必须记录 `TotalDeaths`。

## 1. 三条铁律

| 铁律 | 说明 | 为什么 |
|---|---|---|
| **① 数据驱动优先** | 能放进 `.tres` 的数值，绝不写进 `.cs` | 策划调参零冲突；敌人/词条/轮次全靠配 |
| **② 单向依赖，模块零直连** | `Core` 谁都能依赖，模块之间只能通过事件说话 | 物理上不会改到同一批文件 |
| **③ 场景原子化，大结构用代码拼** | 一个实体一个 `.tscn`，主场景由 C# 运行时组装 | 绕开 Godot 最大的协作雷区 |

## 2. 环境与工程基线

### 2.1 版本锁定

| 项 | 版本 |
|---|---|
| Godot | **4.5.1 .NET 版**（`Godot_v4.5.1-stable_mono_win64`，不是普通版） |
| .NET SDK | **8.0**（Godot 4.x Mono 自 4.2 起依赖 .NET 8） |
| VS Code 扩展 | `C# Dev Kit` + `Godot Tools (geequilim.godot-tools)` |

### 2.2 建工程时立刻做的事

1. **渲染器选 Compatibility**（2D 项目，出包最小，48h 不碰 Forward+ 的坑）
2. 项目设置 → 常规 → 高级设置：开启 **物理插值**；**关闭低处理器模式**（保证手感）
3. **关闭 Godot 的 C# 自动重载**（编辑器 → .NET → 自动重载项目）。原因：4.5 的 C# 热重载仍不稳定，多人协作时常出现"编辑器里脚本变红"。统一改成 VS Code `Ctrl+Shift+B` 手动构建，回到 Godot 自动重载
4. 屏幕分辨率固定（如 1280×720），拉伸模式 `canvas_items`。**单屏游戏不需要相机跟随逻辑**

### 2.3 VS Code 配置（提交进仓库 `.vscode/settings.json`）

## 4. 模块划分与人员分配

### 4.0 分配原则：按「引擎接触度」分层，不按功能平铺

> **团队实况**：除策划外，队友都是**程序专业但没用过游戏引擎**。
> 他们缺的不是 C# 能力，而是 **Godot 编辑器操作经验**。

所以模块不能按功能平铺，必须按**需要打开 Godot 编辑器的程度**分层：

| 层 | 引擎接触度 | 典型工作 | 谁能做 |
|---|---|---|---|
| **L1 纯逻辑** | ⭐ 几乎为 0 | 词条抽取器、`StatBlock`、反射数学、RNG、数据类定义 | **完全不会引擎的人也能做**，只用 VS Code 写 `.cs` |
| **L2 半引擎** | 中 | 玩家控制器、炮弹、敌人移动、伤害管线 | 需要学会「脚本挂节点」「Inspector 改参数」「F5 运行」 |
| **L3 场景层** | 高 | 场景搭建、UI 布局、动画、特效、Autoload 配置 | 需要较熟练的编辑器操作 |

**两条硬规则：**

#### ① 场景守门人制度（最重要的一条）

> **所有 `.tscn` 场景文件与 `.tres` 资源的创建、结构性修改，由固定 1 人负责。其他人一律不碰。**

| | 说明 |
|---|---|
| **理由** | `.tscn` 是 Godot 团队协作的**头号冲突源**。多人同时改一个场景会产生无法手动合并的结构损坏（表现为节点丢失、脚本引用失效、工程打不开） |
| **做法** | 把它变成**单人独占文件类型**，冲突从根上消失 |
| **流程** | 其他人需要新场景 / 新节点时，在群里 @ 守门人并描述需求，由守门人创建 |
| **人选** | **学 Godot 最快的那个人**，不一定是技术最强的 |

#### ② 词条是平铺池，不是解锁树

`PlayerUpgradeData` / `EnemyUpgradeData` **不需要** `Prerequisite` 字段。
GDD 里的"链"只是策划的设计辅助线，**不进游戏逻辑**（详见 GDD §4.0）。

抽取器 = 纯随机加权抽样 + 满层过滤 + 互斥过滤 —— 逻辑极简，几百行就能写完。

## 5. 五大核心契约（Day 1 上午定稿）

### 5.1 事件总线 `Bus.cs`

**不用 Godot 的 `[Signal]`**，改用纯 C# 静态泛型总线：事件是 `struct`（零 GC）、类型安全、且**事件定义分散在各模块自己的 `Events.cs`**——这是避免多人抢同一个 `GameEvents.cs` 的关键。

```csharp
// src/Core/Bus.cs —— 写完即冻结
using System;
using System.Collections.Generic;
using Godot;

public static class Bus
{
    private static readonly Dictionary<Type, List<Delegate>> _handlers = new();

    public static void Sub<T>(Node owner, Action<T> handler) where T : struct
    {
        var t = typeof(T);
        if (!_handlers.TryGetValue(t, out var list)) _handlers[t] = list = new List<Delegate>();
        list.Add(handler);
        owner.TreeExiting += () => Unsub(handler);   // 节点销毁自动解绑
    }

    public static void Unsub<T>(Action<T> handler) where T : struct
    {
        if (_handlers.TryGetValue(typeof(T), out var list)) list.Remove(handler);
    }

    public static void Pub<T>(T evt) where T : struct
    {
        if (!_handlers.TryGetValue(typeof(T), out var list)) return;
        for (int i = list.Count - 1; i >= 0; i--)          // 倒序：允许回调中取消订阅
            ((Action<T>)list[i])(evt);
    }
}
```

### 5.3 伤害管线（全游戏唯一伤害入口）

当前所有伤害都是 1 点，但**管线必须现在就定死**，否则后面加穿透、激光、反伤要重构。

```
攻击发起 → 构造 HitInfo
   ↓
广播 HitInfoCreated（可被词条改写）
   ↓
DamageSystem.Deal(HitInfo)
   ├─① 攻击方修饰器 OnDealDamage(ref HitInfo)
   ├─② 防守方修饰器 OnTakeDamage(ref HitInfo)
   ├─③ 结算最终值 → 广播 EntityDamaged（UI飘字 / VFX闪光 / 音效 / 震屏 / 顿帧）
   ├─④ 扣血
   └─⑤ 若死亡 → 广播 EntityDied（计数 / 胜负判定）
```

```csharp
public struct HitInfo
{
    public Node Source;
    public Node Target;
    public float BaseAmount;     // 当前版本全是 1
    public float FinalAmount;
    public bool IsCrit;
    public bool Canceled;        // 词条可"免疫这次伤害"
}
```

> **关键约定**：无敌帧判定、穿透、激光、反伤，全部实现为 `IModifier` 或走 `Canceled` 标志，**不许写进 `DamageSystem`**。

```csharp
    private readonly Dictionary<Enum, float> _cache = new();
    private bool _dirty = true;

    public void AddModifier(IModifier m) { _mods.Add(m); _dirty = true; }
    public float Get(Enum s) { if (_dirty) Recalc(); return _cache.TryGetValue(s, out var v) ? v : 0f; }
    public bool HasFlag(Enum s) => Get(s) > 0f;      // 开关类词条复用同一套
    // 结算顺序：Base → 所有 Add → 所有 Mul → Override 最后
}
```

**程序 A 只读** `playerStats.Get(PlayerStat.MoveSpeed)`，完全不需要知道词条系统长什么样。
**两条线互不相干**：`PlayerStatBlock` 和 `EnemyStatBlock` 是两个独立实例。

### 5.5 轮次状态机 `RoundDirector`（本游戏最重要的一块）

```
Idle → RoundStart(第 N 轮)
         ├─ 玩家回满 3 血
         ├─ 重置场上敌人（重打时敌人配置完全不变）
         ├─ 从 run_config.tres 读取本轮波次参数
         └─ 广播 RoundStarted
       → Spawning（波次循环）
         ├─ 立即刷第 1 波
         ├─ 每过 WaveInterval 秒刷下一波（**不等上一波清完**）
         └─ 刷完第 WaveCount 波 → 进入 Fighting
       → Fighting（等待清场）
         ├─ 场上敌人清空 → RoundWon  → 三选一强化敌人 → N+1 → RoundStart
         └─ 玩家血量归零 → RoundLost → 三选一强化玩家 → N   → RoundStart（轮次不推进）
       → 若 N > 总轮数 → RunFinished（结算，带 TotalDeaths）
```

**波次相关的三条（容易写错的地方）：**

1. **胜利条件是双条件**：`所有波次已刷完 && 场上敌人数 == 0`。
   只判断其中一个会导致提前误判胜利（常见于"最后一波刚刷出、还没加进计数"的那一帧）。
2. **波次是定时推进，不是清空推进**。到点就刷，不管上一波清没清完。
   这是刻意的压迫感设计，但会带来雪崩风险 —— 见下方保险。
3. **波次参数全部按轮次查表**：`WaveCount` / `EnemiesPerWave` / `WaveInterval`
   都读 `run_config.tres`，策划可独立调整，**不需要改代码**。

> ⚠️ **雪崩保险**：定时推进下，玩家清怪跟不上刷怪会让场上敌人越堆越多。
> 建议保留**敌人存活上限**（如 20，超出则最老的自动离场）作为保险，见 GDD §7-10。

**注意三条：**
1. 失败重打时，**玩家的强化保留，敌人的配置完全不变**。这是保底机制的实现核心。
2. 失败时 `TotalDeaths++` 并持久化，结算要用。
3. 三选一期间游戏**完全暂停**：`GetTree().Paused = true`，但**弹窗 UI 节点的 `ProcessMode` 必须设为 `WhenPaused`**，否则界面自己也会卡住 —— 这是 Godot 新手最常踩的坑。

### 5.6 敌人光学反射移动（v2 新增）

敌人以**恒定的速度大小**在场内做折线运动，撞边界时遵循**入射角 = 反射角**。
对轴对齐的矩形场地，光学反射恰好简化为**速度分量取反**：

```csharp
// src/Enemies/EnemyBase.cs
public override void _PhysicsProcess(double delta)
{
    ReflectOffArenaWalls();
    MoveAndSlide();
}

private void ReflectOffArenaWalls()
{
    Vector2 v = Velocity;
    Vector2 p = GlobalPosition;
    Rect2  b = ArenaBounds.Rect;                   // 单屏场地矩形

    // ⚠️ 四个方向判断不能省 —— 见下方约束 #1
    if (p.X <= b.Position.X               && v.X < 0f) v.X = -v.X;
    if (p.X >= b.Position.X + b.Size.X    && v.X > 0f) v.X = -v.X;
    if (p.Y <= b.Position.Y               && v.Y < 0f) v.Y = -v.Y;
    if (p.Y >= b.Position.Y + b.Size.Y    && v.Y > 0f) v.Y = -v.Y;

    Velocity = v;               // 速度大小天然不变（只翻符号）
}
```

**出生时给定方向（默认正左）：**

```csharp
// src/Arena/SpawnDirector.cs
// 默认：正左方水平移动（vy = 0）
Vector2 dir = new Vector2(-1f, 0f);

// 🔧 扩展点：后续加"斜向出生"类 buff 时，只需在这里覆盖 dir，反射逻辑一行都不用改
// float deg = (float)GD.RandRange(155.0, 205.0);
// dir = new Vector2(Mathf.Cos(Mathf.DegToRad(deg)), Mathf.Sin(Mathf.DegToRad(deg)));

Bus.Pub(new SpawnEnemyRequest {
    Position  = spawnPos,
    Direction = dir,
    Speed     = enemyStats.Get(EnemyStat.MoveSpeed)
});
```

> 📌 **默认 `vy = 0` 是光学反射的特例**：垂直入射 → 原路返回（左右往复）。
> 反射代码之所以要写成通用形式，正是为了将来加方向类 buff 时**只改 `dir`、不动反射逻辑**。

**四条实现约束：**

| # | 约束 | 原因 |
|---|---|---|
| 1 | **方向判断（`v.X < 0f`）不能省** | 没有它，敌人会贴着边界**反复取反**，表现为剧烈抖动。这是 Godot 反射实现最常见的 bug |
| 2 | **只在 `_PhysicsProcess` 里改 `Velocity`** | 帧率无关的物理解算必须走物理帧 |
| 3 | ⚠️ **"摆动" / "潮汐" / "追猎" 词条不能各写一套速度逻辑** | 多个系统同时写 `Velocity` 会互相覆盖，表现为"反射失效"或"敌人乱飞"。见下方"单一写入点" |
| 4 | **不需要给水平分量设下限** | 曾被提议，**已否决**。玩家能 8 向自由移动，会主动走到敌人轨迹上；纯垂直轨迹反而最好打（GDD §3.6） |

> 📌 **约束 3 是后期最容易踩的坑。** 建议 `EnemyBase` 里只保留**一个** `Velocity` 写入点：
> 摆动、追踪、狂暴等所有效果都只产出"速度修正量"，由同一个方法**合成后再做反射判定**。

```csharp
// 推荐结构：所有速度效果汇入一处，反射判定放最后
Vector2 ApplyAllSpeedEffects(float delta)   // 摆动 / 追踪 / 狂暴 … 各自返回修正量
{
    Vector2 v = _baseVelocity;
    if (HasSwing)  v += SwingOffset(delta);
    if (HasTrack)  v += TrackOffset(delta);
    return v;
}

public override void _PhysicsProcess(double delta)
{
    Velocity = ApplyAllSpeedEffects((float)delta);   // ① 合成
    ReflectOffArenaWalls();                          // ② 反射（唯一入口）
    MoveAndSlide();                                  // ③ 移动
}
```

| 6.1 | **销毁后的 Node 不是 `null`** | 判空必须 `GodotObject.IsInstanceValid(node)`。`node == null` 在 Godot C# 里不可靠 |
